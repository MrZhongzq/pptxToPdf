## 一、账号体系（需求 2、3）

### 数据模型

```python
class User(Base):
    __tablename__ = "users"
    user_id: str          # uuid4，主键
    username: str         # unique + index，登录标识
    email: str            # 不唯一（同一人可用同邮箱开多号，非登录标识）
    password_hash: str    # 复用四期的 scrypt:<salt_hex>:<hash_hex>
    role: str             # "admin" | "user"
    status: str           # "active" | "suspended"
    created_at, updated_at
```

**【自主决策】用户名唯一（用户明确要求），邮箱不唯一。** 用户只说了「用户名唯一且
不可重复」。邮箱若也强制唯一，admin 想给同一个人开测试号就得编邮箱。登录一律用
用户名，邮箱只是联系方式，不参与鉴权，因此不唯一不产生歧义。否决的影响：加一条
unique 约束和一条重复校验，改动很小。

**【自主决策】`status` 只有 active/suspended 两态，删除是真删行。** 用户列了「激活/
暂停/删除」三个动作。把「删除」做成软删（status="deleted"）会让「用户名唯一」变得
别扭——删掉的用户名到底能不能再用？真删则语义干净：删了就能重新用。任务表里的
`user_id` 是 nullable 且不加外键，删用户不影响历史任务（那些任务仍可下载，只是不再
归属任何人）。否决的影响：改成软删要同步处理用户名唯一性策略。

### 与四期的关系

四期的 `admin_password_hash`（环境变量）**降级为 admin 账号的引导密码**：

- `init_db()` 之后检查是否存在 role="admin" 的用户
- 不存在且配了 `PPTX2PDF_ADMIN_PASSWORD_HASH` → 创建 `admin` 用户（用户名固定
  `admin`，密码哈希直接取该环境变量，邮箱取 `PPTX2PDF_ADMIN_EMAIL`）
- 不存在且没配 → **不创建**，管理入口继续 503

最后一条延续四期铁律「不设默认值兜底」：绝不因为「方便」而生成一个默认密码。

**【自主决策】admin 引导后，环境变量不再是真相源。** admin 在面板里改密码后，改的是
数据库里的 `password_hash`，环境变量从此只在「数据库里没有 admin」时起作用（即重建
数据库的场景）。否则每次重启都会把面板里改过的密码冲掉。

### 会话

复用四期的 Fernet 签名 cookie，但 payload 从固定的 `b"admin"` 改成 `session:v1:<user_id>`。

四期在 `verify_session` 里显式比对固定 payload，是为了堵住一条真实的攻击路径：
`client_secret` 用同一把 `SECRET_KEY` 加密，数据库里那段密文原样贴进 cookie 就是一张
有效的管理员 cookie（不需要拿到 SECRET_KEY，只需读到数据库）。**这条防护必须保留**：
新 payload 带 `session:v1:` 前缀，验证时先校前缀再取 user_id，`client_secret` 的明文
（Azure 的 secret 字符串）不可能匹配这个前缀。

会话有效期沿用 3 天、登录后刷新（四期用户定的）。

**【自主决策】用户被暂停或删除后，已签发的 cookie 立即失效。** 做法是每次
`require_user` 都回库查一次用户状态，而不是只验签名。多一次 SQLite 主键查询，代价
可忽略；反过来若只验签名，暂停一个账号最多要等 3 天才生效，那这个功能就是假的。

## 二、鉴权分层（需求 4、5）

三个依赖，逐级收紧：

| 依赖 | 语义 | 失败 |
|---|---|---|
| `current_user_optional` | 有 cookie 就解析，没有返回 None | 不失败 |
| `require_user` | 必须已登录且 active | 401 `AUTH_REQUIRED` |
| `require_admin` | 必须已登录且 role=admin | 401 / 403 `FORBIDDEN` |

### /admin 的保护（需求 4）

用户要求「未登录或非 admin 访问 /admin 自动跳转回主页」，并说明理由是没有页面级
WAF。因此**两层都要做**：

1. **前端**：`/admin` 挂载时先打 `GET /api/auth/me`，不是 admin 就 `location.replace('/')`
2. **后端**：所有 `/api/admin/*` 端点走 `require_admin`

前端跳转是体验，后端才是边界。**只做前端等于没做**——绕过前端直接打 API 是最基本的
渗透手法。

**【自主决策】跳转用 `location.replace` 而不是 `href`。** replace 不留历史记录，用户
按浏览器后退不会又弹回 /admin 再跳一次。

### Graph 引擎的登录门槛（需求 5）

前端把 Graph 选项置灰只是 UI。**后端必须同样强制**：`POST /api/tasks/{id}/start` 若
`engine == "graph"` 且未登录 → 401 `AUTH_REQUIRED`。

这里直接撞上项目铁律「绝不静默回退」：**不能因为未登录就偷偷改用 LibreOffice**，必须
明确报错。前端置灰是为了让用户根本选不到，后端报错是为了让绕过前端的人拿到明确答复。

**【自主决策】只拦 Graph，不拦整站。** 需求 5 只说 Graph 对未登录用户灰色，没说未登录
不能用站点。所以未登录用户仍可上传并用 LibreOffice 转换——这与「当前不开放注册」的
设定一致：站点对匿名访客可用，Graph 这种消耗租户配额的通道才要求身份。

## 三、Admin 面板（需求 2、8）

侧边栏分四个板块：

| 板块 | 内容 |
|---|---|
| 用户管理 | 列表、添加、激活/暂停、删除、改密码 |
| Azure 凭证 | 四期既有的 Graph 凭证配置与五步自检，原样搬进来 |
| 访问白名单 | 需求 7 的域名/IP 白名单管理 |
| 系统状态 | 任务统计、存储占用等只读信息 |

**【自主决策】新增「系统状态」板块。** 用户只列了三类内容，但侧边栏只有三项时分栏
的价值不明显；而 admin 最常想知道的就是「现在有多少任务、盘还剩多少」。这是纯只读
聚合，无副作用。否决的影响：删掉一个板块和它的只读端点，不牵动其它。

**【自主决策】admin 不能删除或暂停自己。** 否则一次误操作就把自己锁在门外，而这个
系统没有第二个恢复入口（除非重建数据库）。后端硬拦，返回 400 并说明理由。

## 四、防跨站（需求 7）

用户明确说「这个功能现在没用，先做着」。因此：

- 新表 `AllowedOrigin(origin, note, created_at)`
- 中间件检查 `Origin`（缺失时回退到 `Referer`）的 host 是否在白名单
- **开关 `PPTX2PDF_ORIGIN_GUARD_ENABLED` 默认 `false`**，关闭时中间件直接放行

**【自主决策】默认关闭，且白名单为空时即使开启也放行。** 双保险。这个功能的危险在于
配错就把自己关在门外（尤其是通过 IP 直连的当前部署形态），而它现在又没有实际用途。
两道保险确保「先做着」不会变成「先炸着」。开启且白名单非空时才真正拦截。

**【自主决策】只校验会改变状态的请求（POST/PUT/DELETE/PATCH），GET/HEAD 一律放行。**
跨站攻击的实质是诱导用户的浏览器发起带凭证的**写**请求；拦 GET 只会破坏图片、下载
等正常用法，收益为零。

## 五、并发下载（需求 6）

**后端已经就绪**：Starlette 0.41.3 的 `FileResponse` 原生支持 `Range` 与 206 Partial
Content。实测确认。

前端改造 `downloadResult()`：

1. 先 `HEAD` 拿 `Content-Length`（这一步四期已有，用于预检 410/409）
2. 体积超过阈值时，切成 N 块并发 `GET` + `Range: bytes=a-b`
3. 按序拼成 `Blob` 触发下载

**【自主决策】阈值 4 MiB、并发 4。** 小文件并发的收益被握手开销吃掉，反而更慢；并发
太高对单机 uvicorn 是自伤。4×4MiB 意味着 16MiB 以上的 PDF 才吃满并发，符合本项目
「课件 PDF 通常 2-30MB」的实际分布。两个值都做成前端常量，调整成本极低。

**【自主决策】任一分块失败就整体回退到单请求下载，并且不告诉用户「回退了」。** 这看
似违反「绝不静默回退」，但那条铁律约束的是**转换引擎的选择**——用户显式选了 Graph 就
不能偷偷用 LibreOffice，因为产出物的保真度不同。下载是幂等的字节搬运，两条路径产出
**完全相同的文件**，回退对用户没有任何可感知的差异，报错反而是噪音。这个区别是刻意
的，不是把铁律打折。

## 六、转换后处理（需求 1）

三个选项一期就写进了 `ConversionOptions`，后端一直只落库不实现，前端标着「后端实现中」。

### 6.1 `pdf_outline`（PDF 书签大纲）

**做法**：转换完成后用 pypdf 打开产出的 PDF，为每一页添加一个书签，标题取自对应
slide 的标题占位符文本。

标题提取在 pptx 侧做（`pptx_probe` 已经在解析 slide XML）：取每页第一个
`<p:ph type="title"/>` 或 `type="ctrTitle"` 占位符里的所有 `<a:t>` 文本拼接。取不到就
回退成「第 N 页」。

**【自主决策】取不到标题时回退成「第 N 页」而不是跳过该页。** 书签大纲的用处是在
GoodNotes 里快速跳转，缺页会让大纲和实际页码对不上，比标题不好看糟糕得多。

**与切片路径的交互**：三期的分片转换会把 deck 切成多个 PDF 再合并。书签必须在**合并
之后**加，否则每片的页码基准不同。

### 6.2 `remap_margins`（页边距重映射）

**做法**：把每一页的内容按比例缩小并靠左对齐，右侧留出空白供 iPad 竖屏批注。

用 pypdf 的 `Transformation().scale().translate()` 配合放大 MediaBox 实现，不重排内容、
不损失矢量性。

**【自主决策】留白 25%，加在右侧。** 用户原话是「给 iPad 竖屏批注留出侧边空白」，没
指定比例和方向。25% 是常见的批注栏宽度（一页 A4 横向约 7cm），右侧是右手书写者的自然
选择。做成后端常量，改动成本极低。左撇子或想要更宽留白的需求，等真实反馈再做成选项——
现在做成可配置项属于 YAGNI。

### 6.3 `expand_animations`（动画分步展开）

这是三个里最难的，也是用户在五期明确推迟过的问题 4。

**做法**：在**转换前**改写 pptx。解析每页的 `<p:timing>`，找出按 click 触发的动画序列
（`<p:par>` 里 `<p:cond delay="indefinite">` 的分组），为每个 click 步骤生成一份 slide
副本，副本里把「本步骤之后才出现的形状」删掉。原地把 1 页变成 N 页。

**【自主决策】只处理「进入」动画（entrance），忽略强调、退出、路径动画。**
- 进入动画是「逐步出现」的唯一成因，也是用户抱怨「所有元素叠在一页上」的根因
- 退出动画若也处理，需要表达「先出现后消失」，页数会爆炸且语义含糊
- 强调/路径动画不改变元素的可见性，对分页没有意义

**【自主决策】无法解析时保持原样，并在任务上记一条 warning，不静默。** 若某页的
`<p:timing>` 结构超出上述假设（嵌套触发器、循环、媒体触发等），该页不拆分、原样保留。
这与「绝不静默回退」的处理方式一致：不假装成功，把「这几页没能展开」明确告诉用户。
**新增 `Task.warnings_json` 字段承载这类「成功了但有保留」的信息。**

**【自主决策】展开有页数上限。** 单页展开出的页数上限 20，整份 deck 展开后总页数上限
500。超过则该页不展开并记 warning。没有上限的话，一个做了 50 步动画的 deck 会把 59 页
变成上千页，转换必然超时，且对做笔记毫无用处。

**顺序**：展开必须发生在 `probe()` 之后、`strip_media()` 之后、切片规划之前——展开会
改变页数，而切片规划依赖页数。

## 七、数据库迁移

六期新增三张表（`users`、`allowed_origins`）和一个字段（`Task.warnings_json`）。

`Base.metadata.create_all()` **会**创建新表，但**不会**给已存在的表加列（四期部署时踩
过，`Task.shard_total` 当时是手工 `ALTER TABLE` 补的）。

**【自主决策】本期实现一个最小的列迁移器，而不是引入 Alembic。**

```python
def _ensure_columns(engine) -> None:
    """对照 ORM 元数据与 PRAGMA table_info，补齐缺失的列。"""
```

理由：Alembic 会带来版本目录、迁移脚本、离线/在线两套流程，对一个单机 SQLite 自用
项目是重装备；而「加列」是这个项目唯一实际发生过的 schema 变更类型。最小迁移器约
30 行，覆盖 100% 的已发生场景。**它只加列，不改类型、不删列、不重命名**——这些
SQLite 本来也不支持原地做，真遇到时应该正面引入 Alembic 而不是把这个工具越描越黑。
