# 七期设计：液态玻璃 UI、HTTP v1 转换接口与访问控制

**目标**：把界面从「实心表面」换成液态玻璃质感，修掉五处 UI 缺陷，并新增一条
不经浏览器的 HTTP 转换接口（v1），配套黑名单与升级版防跨站白名单。

**上游需求**（用户原文，10 条，编号按原文）：

1. 登录面板改成全局弹出，配液态玻璃磨砂
2. 全局液态玻璃效果可以上了（记忆里推迟的项）
3. Graph 未登录时点不动但没有变灰效果，文字也要一起变灰
4. 去掉 webui 里的草稿标记（「三期实现」「后端实现中」）
5. Graph 的容量确认弹出位置要和 LibreOffice 的「开始转换」按钮位置统一
6.（原文编号重复）admin 面板卡片拉长、字号加大一号、侧边栏靠左且扁圆
7. HTTP v1 URL 调用转换，直接回传 PDF 文件
8. 防跨站只对 v1 生效，网页永不受影响
9. 白名单加提示「记得把自己解析域名加进来，避免把自己关在门外」
10. 白名单支持通配符与特殊语法；另需网站黑名单，优先级高于白名单

## 一、液态玻璃（需求 1、2）

### 先解决一个前提

二期把玻璃拟态**移除**过一次，理由记在 `surface.css` 的开头：玻璃依赖背后有
内容可透，**在浅色纯色底上只会变成一层灰膜，反而降低对比度**。这条技术判断
今天依然成立——不解决它就直接加 `backdrop-filter`，得到的会是一个更糊、更难读
的界面，而不是「高级」。

**【决策】先给页面一层可透的背景，再上玻璃。** `body` 铺两到三团低饱和径向
渐变光斑（浅色与深色各一套），玻璃卡片浮在上面才有东西可折射。光斑用
`position: fixed` 的伪元素，不随内容滚动，也不参与布局。

### 玻璃的两档

| 档位 | 用途 | 特征 |
|---|---|---|
| `.glass` | 卡片、面板 | `backdrop-filter: blur(20px) saturate(1.6)`，半透明底，1px 高光描边 |
| `.glass-strong` | 模态、悬浮层 | 更高模糊与更实的底色——它盖住的内容更多，需要更强的分隔 |

**【决策】文字与图标不放在玻璃上做半透明。** 只有容器透，内容层不透。玻璃最
常见的翻车就是把正文一起做淡，导致对比度不达标。

**【决策】`prefers-reduced-motion` 下关掉所有玻璃动效**（保留静态玻璃）。这是
无障碍要求，不是可选项。

**【决策】给不支持 `backdrop-filter` 的浏览器留实心回退。** 用
`@supports not (backdrop-filter: blur(1px))` 退回二期的实心表面——那套样式是
经过验证的，不是临时凑的。

## 二、五处 UI 修复（需求 1、3、4、5、6）

### 2.1 登录改全局模态（需求 1）

从「贴着按钮的下拉面板」改成「屏幕居中的模态 + 全屏遮罩」。遮罩自身也是玻璃
（`backdrop-filter`），点遮罩关闭，`Esc` 关闭，打开时焦点移入，关闭后焦点还给
触发按钮。

### 2.2 Graph 禁用态（需求 3）

现在只有 `disabled` 属性，视觉上几乎没变化。改为：整块降透明度、文字与说明一起
转成 `--c-text-faint`、`cursor: not-allowed`、去掉 hover 反馈，并在旁边直接写出
「需登录」而不是只靠 `title`——`title` 在触屏上根本出不来。

### 2.3 去掉草稿标记（需求 4）

- 引擎卡片里的「三期实现」
- 后处理标题旁的「后端实现中」徽章

这两处都已经实现完毕，标记是开发期的残留。

### 2.4 容量确认的位置（需求 5）

现状：LibreOffice 的「开始转换」按钮在 ReadyCard 内部，而 Graph 命中容量风险时
的确认横幅渲染在 ReadyCard **外面**，两者位置不一致，用户要在两个地方找按钮。

**【决策】把确认横幅移进 ReadyCard，占据「开始转换」按钮原来的位置。** 风险
提示与它要拦截的那个动作在同一处，这也是「在不可逆动作发生前就地拦下」的一贯做法。

### 2.5 admin 面板布局（需求 6）

**根因**：`.layout` 在 ≥1024px 是 `minmax(0,5fr) minmax(0,6fr)` 两栏 grid，而
AdminPage 把「侧边栏 + 内容」整个塞进了第一栏，所以卡片只拿到约 45% 的宽度，
Azure 凭证那些长字符串必然换行。

**【决策】给 admin 页用独立的单栏容器 `.layout-wide`，不复用上传页的两栏。**
它们的信息结构本来就不同：上传页是「操作区 + 结果区」的并列，admin 是「导航 +
主体」的主从。

其余按需求：正文字号 15px → 16px（`--font-size-admin`），侧边栏贴左、胶囊形
（`border-radius: 999px`）、选中项玻璃悬浮。

## 三、HTTP v1 转换接口（需求 7）

```
GET /v1/convert?fileUrl=<url>&engine=libreoffice|graph
                &user=<username>&pwd=<password>
                &animations=true&outline=false&margins=false
```

同步：下载 → 转换 → **直接回传 PDF 字节**（`Content-Disposition: attachment`），
不返回任务 id、不需要轮询。

**【决策】参数名用英文小写下划线，不用中文。** 用户原文举例写的是
`书签大纲=False&重映射=False`，那只是在示意含义。URL 里放中文参数名要经过百分号
编码，各家 HTTP 客户端行为不一，调试时极易踩坑。三个后处理分别叫 `animations`、
`outline`、`margins`，与后端 `ConversionOptions` 一一对应。

**【决策】LibreOffice 不要求身份，Graph 必须带 `user`/`pwd`。** 与需求 7 一致，
也与六期「Graph 消耗租户配额所以要求登录」同一条理由。凭据走查询串是用户指定的
形式；我会在文档里写明它会进服务器访问日志与浏览器历史，建议只在受控网络里用。

### SSRF：这条接口最大的风险

`fileUrl` 由调用方给，服务器会去请求它。不设防的话，任何人都能让这台机器去访问
它自己的内网——包括云厂商的元数据端点（`169.254.169.254`，能拿到实例凭证）。

**【决策】强制 SSRF 防护，且不做成可关闭的开关：**

- 只允许 `http` / `https`
- 解析目标主机的 IP，**拒绝**环回（127/8、::1）、私有（10/8、172.16/12、
  192.168/16）、链路本地（169.254/16、fe80::/10）、唯一本地（fc00::/7）、
  未指定（0.0.0.0、::）
- 跟随重定向时**每一跳都重新校验**——只查首个 URL 等于没查，重定向到内网是最
  常见的绕过手法
- 下载体积上限沿用 `max_file_size`，边下边计数，超了立即断开
- 下载超时独立于转换超时

**【决策】拒绝时明确报错，不静默降级。** 与项目一贯的「绝不静默」一致。

### 超时与体积

同步接口不能无限挂着。沿用既有的 `compute_timeout_s`（按页数与体积算），但因为
在拿到文件之前不知道页数，先用一个保守的下载超时，转换阶段再按实际值算。

## 四、访问控制（需求 8、9、10）

### 4.1 白名单只管 v1（需求 8）

**这推翻了六期的一条设计**。六期我把防跨站做成了「校验所有写请求」，并因此加了
两道保险（默认关闭、白名单为空时放行），理由是「配错会把自己关在门外」。

用户明确：**白名单只对 v1 生效，网页永不受影响**。于是：

- 那条「关在门外」的风险不复存在——即使白名单拒绝一切，webui 照常工作
- 因此**移除**「白名单为空时放行」这道保险：空白名单现在的语义变成「v1 谁也
  不许用」，这是一个清晰且安全的默认
- `origin_guard_enabled` 保留但语义收窄为「v1 是否校验来源」；**默认改为开启**

**【决策】v1 的来源判定用请求方 IP 与 `Origin`/`Referer` 两者，任一命中白名单
即放行。** v1 的调用方多半是脚本而不是浏览器，根本不会带 `Origin`；只看头部等于
没有防护。

### 4.2 白名单语法（需求 9）

```
example.com                          精确匹配
*.example.com                        通配：任意子域（不含 example.com 本身）
203.0.113.7                          IP
*.example.com||@except{a.example.com}   通配但排除某些子域
*.example.com||@match{api.example.com}  通配范围内只允许列出的子域
example.com||@no_graph                  该来源不得使用 graph 引擎
```

**【决策】`@except` 与 `@match` 是互补的两种收窄方式，可以叠加。**
`@except{}` 从范围里减去（黑名单式），`@match{}` 把范围缩到只剩列出的（白名单
式）。同时出现时先算 `@match` 再算 `@except`。多个值用逗号分隔。

**【决策】不支持完整正则。** 用户原文提到「通配符和正则语法」，但随后给的四个
例子全是通配与集合运算，没有一个真正的正则。放开正则会引入 ReDoS（一条恶意规则
就能让每次请求都卡住），而且管理员写错一个字符就可能把范围放到全网。通配 +
`@except` + `@match` 覆盖了给出的全部用例。**如果确实需要正则，告诉我，我加一个
显式的 `re:` 前缀并配超时保护。**

**【决策】`||@no_graph` 是修饰符不是匹配符。** 它不影响「是否放行」，只影响
「放行之后能不能选 graph」。命中时若请求指定了 graph，返回明确错误。

### 4.3 黑名单（需求 10）

新表 `BlockedOrigin`，语法与白名单一致（复用同一个解析器）。

**【决策】黑名单在中间件的最前面，网页与 v1 一起拦，直接 403。** 优先级高于
白名单：先查黑名单，命中即 403 返回，不再进入任何后续判断。

**【决策】黑名单按请求方 IP 判定为主。** 网页请求不带 `Origin`（同源），所以对
webui 而言唯一可用的判定依据就是来源 IP。域名形式的条目对 v1 的 `Origin`/`Referer`
以及反向解析生效。

## 五、不做的事

- 不做 v1 的异步模式（提交后轮询）。需求明确要「直接弹出下载」
- 不做 v1 的速率限制。自用场景，且黑白名单已经限定了调用方
- 不给 v1 单独一套凭据体系，复用账号表
- 不做正则（理由见 4.2）
